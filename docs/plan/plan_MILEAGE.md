# plan_MILEAGE — пробег ≤ 400 000 км, иначе решение review

Источники: `docs/setup/code_map.md` (п. 1–3, проверен по коду — актуален, кроме
одного расхождения: фактически `rules.php:44` `approve_max = 62.0`, а code_map
указывает 60.0), grep по `mileage`/`max_mileage` по всему репо.

**Суть правила:** заявка с пробегом больше 400 000 км не может получить `approve` —
решение понижается до `review`. Пробег ≤ 400 000 км на решение не влияет.
Порог живёт в конфиге (AGENTS.md: бизнес-числа не хардкодим), число 400 000
в PHP-коде не появляется.

**Семантика по умолчанию (принято в плане, см. вопрос 1):** сначала решение по
LTV (`DecisionEngine::decide()`), затем пересечение с пробегом: `approve` при
пробеге > 400 000 → `review`; `review` и `reject` не меняются (строже побеждает).
Числа 400 001–500 000 — валидная заявка (валидация `max_mileage_km = 500000`
не трогается) с решением `review`.

## 3. Тесты

Границы — отдельными кейсами:

- **399 999 км, LTV 50.0** → `approve`, `approved_limit` = запрошенной сумме
  (правило не срабатывает; AssessmentServiceTest + DecisionEngineTest).
- **400 000 км, LTV 50.0** → `approve` (граница «не больше», строгий `>`;
  защищает от off-by-one; оба теста).
- **400 001 км, LTV 50.0** → `review`, `approved_limit` = 0 (понижение;
  оба теста).
- **400 001 км, LTV 95.0** → `reject` (строже побеждает — до ответа на вопрос 1;
  DecisionEngineTest).
- **400 001 км, LTV 75.0** → `review` (не «улучшается» до approve, остаётся review).
- **Пробег 0 / 96 000 / 84 000** — регресс: существующие кейсы не меняются.
- **Пустой пробег, два случая** (ApplicationValidatorTest):
  - поле `mileage` отсутствует в payload → `ValidationException` с ключом
    `'mileage'` (`(int)($payload['mileage'] ?? -1)` → −1, до решения не доходит);
  - `mileage => null` (или `''`) → кастуется в **0**, заявка валидна, решение
    считается как для пробега 0 — зафиксировать текущее поведение тестом и
    задать вопрос 3.

Имена — по конвенции, поведение + `assert*`, например
`testApprovesMileageAtThreshold` / `testSendsMileageOverThresholdToReview`.

## 4. Риски

- **`max_mileage_km` = 500 000 (`rules.php:23`, `ApplicationValidator.php:44–45`)** —
  это валидация, а не решение. Новый порог 400 000 — независимая величина.
  Главный риск «рядом»: при реализации «выровнять» потолок валидации до 400 000 —
  тогда диапазон 400 001–500 000 из `review` молча превратится в ошибку валидации
  и сломает саму фичу. Потолок не меняем. Обратный риск: задать в конфиге
  `mileage_review_over_km` больше `max_mileage_km` — правило станет мёртвым;
  защитного кода не планируем, но отмечаем.
- **Смена сигнатур `DecisionEngine`:** мест сборки три — `AppFactory.php:37`,
  `DecisionEngineTest.php:18`, `AssessmentServiceTest.php:27`; вызовов `decide()`
  два — `AssessmentService.php:33`, `DecisionEngineTest.php:24`. Пока обновлены не
  все, `make test` падает — это ожидаемо и лечится в шагах 3–6. Других вызовов
  по grep нет.
- **Приоритет reject vs пробег:** если заказчик захочет «пробег > 400 000 →
  всегда review», поведение и тест `400 001 + LTV 95` изменятся (вопрос 1).
  До ответа реализуем «строже побеждает».
- **Off-by-one на границе:** «не больше 400 000» ⇒ строгое `>`; кейсы 400 000 и
  400 001 фиксируют границу с обеих сторон.
- **Пустой пробег кастуется в 0** (`ApplicationValidator.php:43`): `null`/`''`
  не различаются с реальным «0 км» — молчаливая нормализация. Правило по пробегу
  подсвечивает это, но не ломает: 0 < 400 000 → approve по LTV. Менять каст —
  вне плана (вопрос 3).
- **HTTP-контракт не меняется:** enum решений прежний (`approve`/`review`/
  `reject`), форма ответа та же; фронтенд, `db/schema.sql`, репозиторий не
  затронуты. Правило автоматически действует на оба эндпоинта (`/api/ltv` и
  `/api/applications` — оба через `AssessmentService`), surprises не ждём, но
  на ревью стоит помнить.
- **Не входит:** задача LOAN-12 (`ltv_by_age`), объяснение причины review в
  ответе (поле `reason`), правка фронтенда, правка валидации пробега
  (`max_mileage_km`, касты), изменения БД/миграции, `/health`, feature-тесты
  HTTP-слоя (юнит-покрытия достаточно; при желании — отдельная задача).

## Вопросы, на которые без заказчика не ответить

1. **Reject + высокий пробег:** LTV > 85 даёт `reject`, пробег > 400 000 —
   `review`. Что важнее? План исходит из «строже побеждает» (`reject` остаётся).
2. **Граница:** подтвердить, что «не больше 400 000 км» = ровно 400 000
   проходит без понижения (≤, не <).
3. **Пустой/неизвестный пробег:** сейчас отсутствие поля — ошибка валидации,
   а `null`/пустая строка молча превращаются в 0 км. Устроивает ли это, или
   «пробег неизвестен» должен трактоваться как `review` / отдельная ошибка?
4. **Диапазон 400 001–500 000:** подтвердить, что это валидная заявка с
   решением `review`, а не ошибка валидации (т.е. `max_mileage_km = 500 000`
   остаётся как есть).
5. **Причина review:** нужно ли показывать в ответе, почему решение `review`
   (LTV против пробег), или понижение происходит молча? В план не входит.
6. **Зона действия:** правило одинаково для `/api/ltv` и `/api/applications`
   (общий `AssessmentService`) — так ли задумано?
